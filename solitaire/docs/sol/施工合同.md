## 3. 方案依据与复用决定

### 3.1 当前工程事实

- `project.godot` 当前基准为 `1280×800`，未配置与旧版等价的竖屏拉伸策略。
- `presentation/cards/card_view.gd` 当前用 `_draw()` 生成临时纸牌；尺寸为 `90×126`。
- `presentation/board/board_view.gd` 当前采用横屏坐标，基础堆起点为 X=860，不符合旧版 1080×1920 布局。
- 这些实现只可作为交互原型复用，不能作为美术与布局验收基线。

### 3.2 旧版一手依据

- `Classes/AppDelegate.cpp`：`designResolutionSize = Size(1080, 1920)`；`setDesignResolutionSize(..., ResolutionPolicy::FIXED_WIDTH)`。
- `cocosstudio/ui/GameLayerHD.csd`：根 Layer 与 Panel 均为 `1080×1920`；牌位尺寸为 `146×220`。
- `Classes/AppConstant.h`：运行时 `POKER_SIZE = Size(148, 220)`。布局占位采用 146×220，实际纸牌内容允许 148×220 的 2 px 差异，执行者不得混成第三套尺寸。
- `Classes/manager/AtlasManager.cpp` 与 `Classes/object/CardSprite.cpp`：纸牌正反面从 `car_new_0_1.atlas/png` 按 region 组合；默认牌背使用 `card_bg_0` 系列。
- `Resources/game/car_new_0_1.png/.atlas`：主纸牌/牌背 region 源图，atlas 尺寸 `1044×2034`，牌背 region `142×218`。
- `Resources/ui.png/.plist`、`Resources/ui1.png/.plist` 与 `GameLayerHD.csd`：核心牌桌槽位和操作按钮的原 UI 来源。
- 旧牌局与规则依据沿用历史轮次已取证的固定 commit、倒序解码、列优先三角发牌事实，并须在 WP-02 重新提交确认。

### 3.3 Godot 官方依据

- Godot 官方 Multiple resolutions 文档将 viewport width/height 定义为设计尺寸；`canvas_items` 可按基准尺寸缩放 2D，`keep_width` 保持宽度并在更高设备上扩展可见高度。
- Godot 官方 Importing images 文档确认 PNG 默认可作为 `Texture2D` 导入；2D filtering 由 CanvasItem/项目设置控制；2D 原图宜使用 lossless 以避免附加压缩伪影。
- Godot 官方 Import process 文档要求工程内图片通过 ResourceLoader 使用导入结果，避免直接依赖 `.godot/imported` 内部路径。

参考：

- https://docs.godotengine.org/en/latest/tutorials/rendering/multiple_resolutions.html
- https://docs.godotengine.org/en/latest/tutorials/assets_pipeline/importing_images.html
- https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html

### 3.4 复用与不复用决定

1. 复用现有 Core、Deal、Application 和测试结构，先复核再修复；禁止无依据重写。
2. 复用固定 Cocos commit 的牌面、牌背、牌桌背景/槽位、核心玩法按钮美术及其布局规格；只复制所需 Git blob 到 Godot `assets/legacy/**`，不复制商业化、鱼、商店或无关资源。
3. Cocos Spine/atlas 格式不直接作为 Godot 运行依赖。允许从固定 atlas 确定性生成 Godot `AtlasTexture`/region 元数据或无损裁切的 PNG；映射必须可追溯、可测试、不得重绘或改变视觉内容。
4. Godot 设计基准固定为 `1080×1920`，使用 `canvas_items + keep_width` 复刻 `FIXED_WIDTH`；不同设备高度变化通过上下安全区/锚点处理，不把 1080×1920 非等比拉伸。
5. 不移植 Cocos Scene Tree/Manager 耦合架构，不引入 Cocos/Spine runtime，不让 Presentation 成为状态源。
6. 旧版动画可以在后续阶段重做；本阶段要求静态美术与交互闭环视觉一致，不要求完整复制旧 Spine 动画。

风险与验证：atlas region 的原点/旋转、Cocos Y 轴方向、146/148 宽度差异、FIXED_WIDTH 高屏扩展都可能导致视觉漂移；必须用映射单测、1080×1920 MCP 截图和至少一个非 9:16 高屏截图验证。

## 4. 不可破坏约束

1. Cocos 仓库及任何工作树、索引、分支严格只读；只允许 `git show`、`git cat-file`、`git rev-parse` 等对象读取。
2. Scene Tree 不是 Game State；`GameState` 是牌局唯一真相源。
3. CardData/Rules/Move/GameState 不继承 Node，不依赖 UI、网络、广告、平台或分析。
4. 玩家、Hint、Auto Complete、Replay 全部通过统一 `Move + MoveExecutor`；UI 不直接写牌堆。
5. Deal Repository、Deal Selector、Rules、未来 Assist 保持独立；本阶段禁用 DDA/Assist/Solver。
6. Undo 使用用户命令边界的深拷贝 snapshot。
7. 旧 52 字节编码、ASCII Card ID、倒序、三角发牌必须由静态 Golden Test 锁定。
8. 保留 `addons/godot_ai/**`、`mcp_verify.tscn`、icon 与无关用户内容。
9. 禁止引入 Cocos2d-x 或 Spine runtime 依赖；静态原图/atlas 数据转换必须离线、确定性、可复现。
10. 只有负责人可发布、启动或恢复执行者；Sol 不代发、不指挥施工会话。
11. 执行者必须通过已安装的 Godot AI MCP 工作。CLI 可辅助批量数据和最终复跑，但不能替代实时编辑器验证。
12. 已有旧终局候选不得被描述为通过；所有新增结论必须进入当前 WP 证据确认流程。
